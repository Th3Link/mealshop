# Native cooking history and learning

Use household navigation History for actual completed cooks and an owner-only Learning settings
section within it. A compact dated list shows recipe, servings, actual attendees, reported effort
and household/individual ratings without decorative dashboards. Link back to the exact recipe
revision. Record a cook from history (manual) or from a completed cooking session, keeping the
completion confirmation and household visibility clear. Never turn a planned meal into history.

The editor uses visible labels, an existing-recipe selector, actual-date input, attendee selectors,
optional effort and native labelled 1–5 selects with Not rated. Session-derived recipe/servings are
locked to the actual session; no guessed effort is prefilled. Explicit save, cancel, dirty protection,
confirmed deletion, loading/error/conflict states and focus restoration follow existing views.

Learning is an explicit owner-controlled opt-in. Explain who can see ratings, which profile ratings
are used, that changing scope starts fresh, and the separate effects of reset versus history deletion.
Use a clear current state and ordinary controls; never present a generic enable-all consent banner.

Planning suggestions retain Review and the current dietary warning/review flow. Show compact reason
lines with actual sample counts and whether a recipe is a discovery choice; use words alongside icons.
Ratings affect order only after current hard constraints. Do not label a recipe safe, imply clinical
confidence or hide unknowns. Keep scope, profile and history revisions tied to one server response.

Use Nextcloud Vue components, theme tokens and existing typography; Taste guides alignment/spacing
and UI/UX Pro Max guides form feedback/confirmation. No landing-page assets, palettes, fonts, resets
or new UI framework. Verify EN/DE, light/dark, keyboard, 1440/390/320 px, axe and screenshots in the real
Nextcloud instance, with only owned synthetic fixtures.
